# فحص الانتقال للإنتاج — 2026-09-29

هذه مراجعة للكود الموجود، وليست إثبات نشر. حافظ التحديث 3.1 على تصميم الأقسام ومخطط قاعدة البيانات.

| الجزء | الموجود والقرار |
|---|---|
| FastAPI | خادم واحد في server/app.py؛ تشغيل بعامل واحد لأن إشعارات المتصفح في ذاكرة العملية |
| البيانات | Supabase PostgreSQL عبر REST/RPC؛ ملفات SQL 001–003 ثم مهاجرة maritime_advisor_hardening، مع RLS ومعاملات المراجعة وسجل التدقيق |
| SQLite القديم | لا توجد قاعدة SQLite فعلية ضمن الملفات المتاحة؛ لم تُحذف بيانات ولم ننفذ نقل بيانات غير موجودة |
| الدخول | ID يُحل داخليًا إلى حساب Supabase؛ كلمة مرور ثم TOTP؛ الصلاحيات التشغيلية تتطلب AAL2 وعضوية فعالة |
| تحديث المصادقة | المتصفح يستخدم FastAPI لعمليات Auth/MFA/refresh/logout؛ لا يحتوي مفتاح Supabase، حتى المفتاح العام |
| الأرشيف والإحصاءات | نُقلا من REST المباشر إلى مسارات FastAPI محمية، مع ترقيم الصفحات وتصفية UTC |
| الصور | JPEG/PNG/WebP حتى 10MiB، فحص المحتوى، Storage خاص بمسارات مبنية على بصمة المحتوى؛ روابط عرض 60 ثانية |
| الأحداث | REST JSON أو multipart، مع event_id ثابت وإعادة إرسال متطابقة؛ أضيف received وevent_id للاستجابة الناجحة دون كسر الحقول السابقة |
| WebSocket | الموجود للمتصفح فقط: تذكرة قصيرة أحادية الاستخدام ثم إشعارات وإعادة جلب البيانات |
| Jetson WSS | غير منفذ بعد؛ يُنفذ ويُختبر مع عقد Level 2 في مرحلة الربط. REST telemetry/claim/ack موجودة حاليًا |
| الأوامر | قائمة قدرات مسموحة، تحقق صلاحية/حداثة، idempotency وسجل حالات. القبول/الرفض لا ينفذ أمر طيران تلقائيًا |
| انقطاع Jetson | طابور محلي دائم وإعادة الإرسال حتى ACK مطلوبان في Level 2، وغير منفذين بهذه الحزمة |
| التشغيل | APP_ENV واضح، فحص HTTPS والأسرار وCORS عند الإقلاع، لا reload، إخفاء Swagger في الإنتاج، PORT من البيئة |
| النشر | Supabase منشأ ومهيأ في فرانكفورت؛ Docker + render.yaml + GitHub Actions جاهزة كملفات ولم يُنشر الموقع أو Render. لا اشتراك مدفوع أُنشئ |
| الواجهة | index.html واحد قابل لخدمة Render أو GitHub Pages؛ يستخدم أصل الصفحة افتراضيًا وWSS تلقائيًا مع HTTPS |

## ما يتطلب بيانات منك في مرحلته

1. المصدر رُفع إلى GitHub؛ راجع نتيجة Actions على آخر commit قبل أي نشر.
2. Supabase أُنشئ بالفعل؛ المتبقي مراجعة إعدادات Auth وإدخال الأسرار في إعدادات الخادم مباشرة واختبار المدير الذي جرى تجهيزه.
3. قاعدة SQLite الأصلية إن أردت نقل بيانات فعلية؛ نأخذ نسخة ونعد تحويلًا قابلًا للتحقق قبل أي تبديل.
4. عقد Level 2 وكوده: هوية الجهاز، معدل التليمترية، إطارات GPS والارتفاع، أوامر follow/resume، قواعد ACK/retry/expiry، وما يحدث عند الانقطاع. لا نفترض صلاحية الطيران من قبول حدث.
5. تفويض Render ومراجعة المنطقة والخطة؛ Blueprint يقترح starter ويجب مراجعة التكلفة قبل الإنشاء.
6. هاتف Authenticator وJetson وشبكة 4G لاختبار التكامل النهائي.

## حدود مهمة للتشغيل

- لا توسع الخادم إلى عدة instances/workers قبل إضافة ناقل إشعارات مشترك؛ واجهة المتصفح تعيد الجلب الدوري كوسيلة استعادة.
- انتهاء مهلة المراجعة يتطلب عاملًا مستمرًا. بعد الانقطاع يعالج العامل الأحداث المتأخرة؛ لا يضمن موعدًا لحظيًا أثناء توقف الخادم.
- تحديد المصدر الموثوق لعناوين reverse proxy مطلوب في Render حتى لا يصبح حد المحاولات مشتركًا بين الجميع. لا نضع FORWARDED_ALLOW_IPS=* تلقائيًا.
- الروابط الموقعة قد تبقى صالحة حتى انتهاء 60 ثانية بعد إلغاء صلاحية الحساب.
- عامل المصادقة يفرض التحقق في Supabase الحقيقي؛ اختبارات الشبكة المحلية لا تثبت إعداد مشروع مستضاف.
